# 002 授权

授权决定谁可以发起工作，以及工作可以包含什么。本文建立在 [001 领域模型](001-domain.md)之上。

宿主强制执行允许名单、规则和 Mandate。消息、评论和引用的文档是决策输入，不能改变这些权限。

## Trigger 的两条路径

### Eval：决定是否开始工作

Source 记录消息是否指向智能体：`mention` 表示提及机器人或智能体账号，`direct` 表示私信。准入层检查发送者和 Source 的 Policy：

- 允许名单中的人向智能体发送消息，构成明确请求。
- 人在已有 Ticket 的 Thread 上发送的后续消息遵循下列规则。
- 其他人类消息使用其接收范围的准入表。
- Source 机器人名单中的机器人可以产生推断型候选，但不能产生明确请求。其他机器人不予准入。

### Subscription：继续已有工作

订阅 Thread 上的每条消息都作为上下文送达其订阅 Ticket，包括机器人和 CI 的消息。这种发送绕过准入层，不授予新权限。每个 Ticket 仍受其 Mandate 限制。

人在 Ticket 自身 Thread 上的消息由该 Ticket 的 Executor 决定。主 Session 将消息附加到 Ticket 时也是如此。Executor 拥有消息期间，它不经过 Eval，也没有 Decision。每个 Executor 要么在 Ticket 范围内处理请求，要么将其交回，以便路由到其他位置。

Ticket 活跃期间，即使人移除了它的 Subscription，责任仍持续。这也包括未经人停止而结束、且消息正等待恢复它的 Ticket。

主 Session 会收到后续消息通知。Executor 拥有消息期间，主 Session 只能应人的请求停止工作；接受、附加、忽略和重新排队都会被拒绝。停止仍须以如下所述的后续消息强度通过准入层。

### 交回和释放后续消息

当消息请求超出 Ticket 范围的工作，或属于另一个 Ticket 时，Executor 将其交回一次。Ticket 保留其 Subscription。如果附加的 Thread 无关，Executor 会交回它在那里的责任消息。

只有不再有 Ticket 拥有消息时，它才进入新的 Eval。候选中包含 Executor 给出的原因。准入层将其作为该 Thread 上的普通消息判断，主 Session 可以接受、附加到别处或忽略它。交回 Ticket 不曾拥有的消息（如机器人消息或人已经送往 Eval 的消息）不会将其排队。

Ticket 结束时，会释放 Executor 未读或未接手的后续消息。这包括从未送达 Executor 的消息，以及在最后一次 Report 或轮次结束之后送达、且未被确认、答复或交回的消息。其他 Ticket 均不拥有该消息时，每条释放的消息都进入 Eval。停止只结束被停止 Ticket 的工作。

被停止的 Ticket 不会将停止消息再次送入 Eval，除非另一个 Ticket 将其交回。停止它的主 Session 可将消息其余部分作为新工作接受。

人可以从面板将被拥有的后续消息送往 Eval。如果主 Session 随后把它附加回活跃 Ticket，Executor 会再次收到它。没有有效判断覆盖消息时，面板也提供重新评估。

### 仅供上下文的订阅

Executor 可以关注相关 Thread（如另一个 Issue 或拉取请求）以获取上下文。其消息会送达 Ticket，但不授予权限或后续消息强度。除非主 Session 附加该 Thread 的消息，否则其中的人类消息不会恢复已结束 Ticket。主 Session 关于其他工作的备注也仅是上下文。

未送达任何 Ticket 的人类消息，包括 Ticket 均被人停止的 Thread 上的消息，走 Eval 路径。机器人消息无论是否送达订阅 Ticket，都会独立走该路径。

## 强度

| 强度 | 情况 |
| --- | --- |
| explicit（明确） | 名单中的人向智能体发消息，或在已有 Ticket 的 Thread 上跟进；准入表单元格设为明确请求 |
| inferred（推断） | 不在名单的人在已有 Ticket 的 Thread 上跟进，除非其准入表单元格为明确；准入表单元格设为推断候选；Source 机器人名单中的机器人向智能体发消息或在 Source 接收全部消息的范围内发消息 |
| 不准入 | 其他机器人的消息、准入表忽略的所有内容，以及接受模式为 `off` 时的所有推断情况 |

对不在名单上的人，即使 Thread 已有 Ticket，明确准入单元格仍优先，并在所有接受模式下生效。否则其后续消息为推断型，且在 `off` 模式下不准入。仅供上下文关注的 Thread 上的消息使用准入表，而非后续消息强度。

## 准入

每个 Source 的 Policy 都有准入表，行表示接收范围：

- **飞书：** 每个已配置群、机器人接收提及的其他群，以及私信。只有飞书卡片上的**其他群**设为**仅 @** 时才接收其他群。
- **GitHub：** 新 Issue、新拉取请求、评论和默认分支 CI。

每行最多三个单元格，决定消息成为明确请求、推断候选还是不产生候选：

| 单元格 | 可选值 | 默认值 |
| --- | --- | --- |
| 在名单中、未指向智能体 | 推断、忽略 | 推断 |
| 不在名单中、指向智能体 | 明确、推断、忽略 | 忽略 |
| 不在名单中、未指向智能体 | 推断、忽略 | 忽略 |

未指向智能体的消息对应的单元格只在 Source 接收全部消息的范围内可用，例如设为**全部消息**的飞书群，或启用接收全部开关的 GitHub 范围。CI 结果没有发送者，因此其行只提供最后一个单元格。机器人消息使用机器人名单，不使用这些单元格。

将“不在名单中、指向智能体”设为明确，可让该范围内任何人通过提及智能体请求工作，适用于专用支持群。推断候选仍取决于接受模式。后续消息通常绕过此表，但明确单元格仍授予明确强度。

准入表属于 Policy 版本。弱化单元格不会立即停止依据它接受的打开 Ticket，但在恢复前重新验证时可能撤销其 Mandate。

### 机器人和自动评审者

宿主将 GitHub App、以 `[bot]` 结尾的登录名及飞书机器人识别为机器人。Source 可以列出 `dependabot[bot]` 等机器人，使其消息成为推断候选。它们必须指向智能体，或发布在接收全部消息的范围内。它们不能提出明确请求或停止 Ticket。

使用普通账号的自动评审者在宿主看来是人。其评论送达订阅 Ticket 并生成后续消息通知。团队提示词必须将这些账号标识为自动评审者。

## 候选路由

主 Session 使用 `orchestrator_route` 路由明确候选。一项调用可包含多个接受、附加、停止或忽略决定。每项独立处理：某项被拒绝或缺字段不会阻止其他项运行。

推断候选通常需要完整研判。有一个简化路径：如果卡片清楚表明候选不涉及任何启用规则，例如普通闲聊或无关讨论，主 Session 可以直接忽略。Decision 记录 `ignoredFromCard`，以区别于规则研判。主 Session 在 Policy 提示词部分读取启用规则。

接受推断候选始终需要研判。直接接受会拒绝准入层未认定为明确的 Trigger。

## 接受模式与规则

接受模式属于 Policy：

| 模式 | 效果 |
| --- | --- |
| `off` | 推断内容均不成为候选，例如未指向智能体的消息、机器人消息或不在名单者的后续消息 |
| `observe`（默认） | 研判推断候选；正面研判记录为标记“本会接受”的忽略，不接受任何工作 |
| `auto` | 推断候选的正面研判会将其接受 |

明确请求在所有模式下均有效。先使用 `observe`，审查记录的 Decision 后再切换至 `auto`。每次研判对每条启用规则恰好判断一次，无论是否匹配。主动接受至少需要一条匹配规则。

每条规则描述一种主动工作。Ticket 的 Mandate 记录匹配规则，其 Executor 收到这些规则的名称和指令。

对该 Ticket，规则中的流程和沟通要求优先于默认值。静默规则可以禁止确认；评审规则可以指定合并前所需的评审人和批准。适用于全部 Ticket 的要求应放在团队提示词部分。

## Policy 版本

规则、接受模式和各 Source 的 Policy 共同构成 Policy 版本。每个 Mandate 记录其被接受时的版本。

版本变化会丢弃运行中的 Eval，并将其 Trigger 重新排队。同时会向每个受影响的活跃 Ticket 发送 Policy 已更改的 Input，说明是否：

- 匹配规则发生变化（包括新文本）或不再适用；
- 请求者可能不再能够发起工作；或
- 不再接受主动工作，例如模式已从 `auto` 改变。

未受影响的 Ticket 不收通知。变更不会立即撤销活跃 Ticket 的 Mandate。

Source 配置独立于 Policy，控制什么进入系统：读取哪些群，以及某范围接收全部消息还是仅接收提及。Mandate 记录其 Source 和接收范围。恢复要求 Source 仍监听该 Thread，但不要求仍接收其中全部消息。

Source 关闭时回复会等待；如果 Source 不再监听目标对话，则回复被丢弃。

对 Executor 如何处理自身结果的条件（如何时可以合并）不决定谁可以授权工作，属于智能体指令，而非 Policy。

## 恢复和停止

已结束 Ticket 保留其 Mandate。任何人在其自身 Thread 上发消息都可以无需新的 Eval 或 Decision 恢复同一工作。机器人和 CI 不会唤醒已结束的 Ticket。Executor 判断请求是否符合范围，不符合时结束该轮。

只有三个操作改变 Mandate：接受创建它，人的停止操作撤回它，重新验证失败撤销它。被人停止的 Ticket 保持结束且不再接收消息。在那里请求新工作需要重新接受。

### 恢复前重新验证

Source 必须仍监听原始 Thread。其他检查取决于 Mandate 的依据：

- 明确后续消息 Mandate 通过。
- 推断 Mandate 需要 `auto` 模式，且匹配规则仍启用。
- 通过准入表单元格准入的 Mandate，在当前表和发送者名单状态下仍须获得至少原来的强度。因此将发送者移出名单可能撤销通过名单内发送者单元格接受的 Mandate。
- 机器人的 Mandate 要求该机器人仍在 Source 的机器人名单中。推断型准入表和机器人 Mandate 还需要 `auto` 模式及启用的匹配规则。
- 其他 Mandate 要求发送者仍在 Source 的允许名单上。

验证失败时，Ticket 保持结束，不接收等待的任何消息。每条消息按未送达任何 Ticket 处理；没有其他 Ticket 拥有时进入 Eval。主 Session 不会被告知消息已送达 Worker。处理暂停后也适用此规则。附加到该 Ticket 会被拒绝，后续工作需要重新接受。

- **人在 Thread 中说“停止”是一条普通 Trigger，** 由 Eval 决定停止。Executor 不能宣称人要求它停止。
- **面板中的停止是命令。** 它直接作用于 Ticket，并记录为手动停止。
- **等待条件属于 Source。** 例如“连续 N 小时没有负责人”应由 Source 自行等待并再次检查；Eval 从不等待。

## Eval 未完成时

时限从候选送达主 Session 时开始。等待送达所花的时间不计入，未送达的候选永不超时。

超时的 Eval 将 Trigger 重新排队以再次尝试。连续重试两次后，第三次超时记录为 `unavailable`。研判失败也记录为 `unavailable`；之后的 Trigger 可以启动新 Eval。Policy 变化或依据过期 Policy 作出的决定会记录 `unavailable`，并立即按当前版本将该批次重新排队。

`evals` 健康项报告过去一小时未解决的 unavailable Decision。`scripts/dsh-superagent status` 包含该错误。

只有同时满足以下条件时面板才请求人工关注：unavailable Decision 不满 24 小时、仍是其 Thread 上最新的 Decision、未被忽略，且 Thread 未排队也未在评估中。人可以重新评估 Trigger 或忽略该问题。
